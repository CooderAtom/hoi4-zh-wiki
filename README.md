## 二·补、翻译单元"可见性"审计（第 16 轮）

本轮发现并修复了一个**让已完成译文无法被读者看到**的缺陷，同时留下了两份可复现的量化工具。

**缺陷**：抽取器 `tools\units.mjs` 的 `collectUnits()` 会把**含嵌套块级标签的整块**（例如一个 `<td>` 里套 `<ul><li>…`）登记成一个"整棵子树"翻译单元；而渲染器 `applyTranslations()` 出于安全考虑**只重建不含嵌套块级标签的叶子块**（`hasBlockContent()` 为假）。结果是这类单元被翻译了、存进了记忆库，却永远不会被套用到页面上。

**实测规模**（`node tools\08g-render-audit.mjs`）：

| 类别 | 已译字符 | 仍为英文 |
| --- | --- | --- |
| 叶子块单元（渲染器可整体重建） | 169 万 | 1,153 万 |
| 文本节点单元（文本节点通道逐条替换） | 257 万 | 595 万 |
| **被遮蔽的嵌套块单元（已译但永不下发）** | **52.1 万（10,953 个单元）** | — |

被遮蔽最多的页面：`Achievements`（653 个单元 / 10.5 万字符）、`Faction`（336 个）、`Experience`（392 个）、`List of political advisors`（376 个）。

**修复**：`collectUnits()` 不再为含嵌套块级标签的块登记整棵子树单元，改为**继续下钻**，让其中真正的叶子块各自成为"渲染器确实能套用"的单元；同时修复 `walkInline()` 遇到嵌套块级标签时不继续下钻、导致这些文本**连单元都算不上**的问题。

**修复已验证不影响渲染结果**：对 `Achievements` 逐页对比修复前后的构建产物，字节数、汉字数、英文词数、`<img>`/`<a>`/`<ul>`/`<li>`/`<td>`/`<tr>`/`<p>`/`<div>` 计数**全部零差异**——因为修复只改变"抽取哪些单元"，不改变"如何渲染"。渲染器行为**未作改动**。

> **一次被实测否决的尝试（记录在此以免重蹈）**：曾试着让渲染器也重建嵌套块。对 `Achievements` 构建后实测：`<ul>` 471→26、`<li>` 2403→505、`<img>` 2590→1132、`<a>` 2815→1375——因为这类单元的译文是以空格线性化存储的纯文本，重建时把嵌套标记**整片压平**。随即回滚，并改为上述"只修抽取、不动渲染"的方案。第二次尝试"按英文段长比例把译文切回各文本节点"同样被实测否决：汉字数 23,620→18,729，**净损失 4,891 个汉字**（切割打散了中文句子）。两次都以页面级结构计数对比作为验收依据。

**这套审计的价值**：它把"翻译完成度"与"读者可见度"区分开。此前 `08c-real-coverage` 统计的是"记忆库里有没有"，现在另有 `08g-render-audit` 回答"页面上到底下发了没有"。**两者口径不同、分母不同（14.0M vs 21.7M 字符），不应互相比较**，各自回答各自的问题。

> ⚠️ **本轮完成度数字发生了口径变化，不可与上一轮直接比较。** 修复 `collectUnits()` 后单元表从"整棵子树"改为"可下发的叶子块"，分母因此由 1,401 万字符降为 845 万字符，同一个记忆库算出的完成度由 17.4% 变为 21.7%。这**不是本轮新增翻译带来的提升**（本轮实际新增约 4.8 万字符译文），而是分母变得更贴近"真正能下发的内容"。新分母更小、更严格，也更接近读者的实际体验。

### 第 17 轮：合并工具的三处加固与一个**尚未修复**的遗留缺口

**一、单元键失效的自动恢复（`tools\10-merge-pageblocks.mjs`）**

单元键是内容哈希，因此 `collectUnits()` 一改，旧键就全部失效——本轮有 **1,195 条**已翻译条目因此无法入库。处理方式是**不丢工作**：

- 块文件自带 `en` 的，直接以文件为准；
- 只写了 `{k, zh}` 的旧文件，**回到翻译记忆库按中文反查英文**（先精确匹配，再按占位符骨架匹配）——恢复 **578 条**；
- 剩余 617 条经 `tools\classify.mjs` 判定为**代码片段或公式残留**（如 `on_actions = { on_monthly = ... }`、`{\displaystyle F*(\text{max}...)}`），本就**不应翻译**，现按"设计上跳过"计数而非报错。

新增 `--strict` 开关：需要严格校验新写的块文件时启用，会拒绝任何键已失效的条目。合并结果：`blocks=55 items=5485 accepted=4868 codeSkipped=617 errors=0`。另新增 `isMathArtifact()`，把当年 MathJax 报错时误存进记忆库的 LaTeX 源码永久挡在门外。

**二、共享单元优先：投入产出比最高的翻译方向**

新增 `tools\08d-impact.mjs` / `08e-export-impact.mjs`，按 **「英文长度 × 出现页数」** 排列待译条目。收益极大：一句 65 字符的 `牵引式火炮、牵引式反坦克炮、牵引式防空炮、牵引式火箭炮` 一次翻译，即出现在 **89 个页面**上；本轮 29 条 / 1,571 字符的一批，覆盖 **126,942 字符·页**。实测站点"已下发字符"由 426 万升至 **533 万（+107 万）**。

**三、`collectUnits()` 与 `walkInline()` 的嵌套块下钻修复**

见上节。修复后记忆库不再累积"永远发不出去"的条目。

**四、遗留缺口：内联元素的译文仍不下发（本轮**试图修复但已回滚**）**

`collectUnits()` 会把内联元素（`<i>`、`<b>`、`<span>` 等，即 `inline:` 单元）登记为翻译单元，并递归登记其中的内联子元素；但渲染器的第二遍只处理**文本节点与属性**，**从不重建内联元素**。因此这类译文同样存在"存了但发不出去"的问题（例如 `By selecting this ⟦0⟧ they will permanently affect…` 在 111 个页面上仍是英文）。

本轮实现了该修复并**实测后回滚**：第一遍已把外层块整体重建，此时这些内联元素已是**译文重新解析出的片段**，再重建它就会丢掉它自己的标签。对 `Afghanistan` 实测：汉字 +1,193，但**丢失 43 条 `<a>` 国家链接**（国旗锚点保住了，包裹国名的锚点被丢弃）。随后又尝试"把图标整段（含其 `<a>`）深拷贝回来"，`<a href>` 仍为 1356→1313——因为丢失的锚点包裹的是**纯文本**而非图片，深拷贝救不了它。

回滚后实测：汉字 +897、英文词 −514、**丢失链接 0**、`<img>`/`<ul>`/`<li>`/`<td>`/`<tr>`/`<p>`/`<div>` 计数**全部零差异**。**尚未修复**，已在代码注释中写明根因与安全修复方向（调整套用顺序：先译子节点，或把片段与其原始节点重新配对），需要整站级验证才能启用——**一个会静默丢链接的渲染器，比保留英文更糟**。

### 第 18 轮：第三种方案同样被实测否决，该缺口按"暂不修复"处理

按上一轮设想的"调整套用顺序"实现了第三版：在块重建**之后**、自底向上（深度优先）单独遍历内联元素，只替换其内部文本、保留其子元素。理论依据是：块译文中的 `⟦n⟧` 会被替换回**原始英文片段**，因此 `href` 与 `data-wiki-title` 应当幸存。

### 第 31 轮：查清"3 条已译单元查不到"的真因（工具缺陷，非内容缺陷）

上轮我报告 `08b-page-gap.mjs` 把 `0.1x⟦0⟧`、`[a]`、`[b]` 误报为未译，并猜测是"剥掉 `⟦0⟧` 再查库"导致。**这个猜测是错的**，本轮查清了真正的原因，而且原因在别处：

`tools/translate.mjs` 的 `Store.set()` 第 59 行是：

```js
if (typeof zh !== 'string' || !zh.trim() || zh === en) return false;
```

**当"译文"与英文逐字节相同时，`set()` 拒绝写入。** `[a]`、`[b]` 中英完全相同，`0.1x⟦0⟧` 同理，所以它们**按设计就不会进入翻译记忆库** —— 内容本身没有任何问题，这三条本来也无文字可译。

真正有缺陷的是**合并器的计数**：`10-merge-pageblocks.mjs` 无条件执行 `store.set(...); added++;`，于是把这三个"什么都没写入"的条目也算进 `accepted`。这使 `accepted` **系统性虚高**，并让我上轮误以为存在数据丢失。

已修正为按 `set()` 的返回值分别计数，并新增 `noop` 计数：

```js
if (store.set(en, it.zh)) added++;
else noop++;
```

修正后整库重跑 `10-merge-pageblocks.mjs` 输出：`items=6790 accepted=6 noop=6167 codeSkipped=617 errors=0`，**记忆库大小不变（18,691）**，证明合并是幂等的、没有重复写入。

> 教训：**误报和真实缺陷要分开归因。** 上轮我把一个"报表假阳性"归因到了错误的位置；本轮 `key(en)` 返回的哈希恰好等于单元键（`wzat1w` 等）这个反常现象，才把线索指向了正确的 `set()`。

#### 二、67 处裂图：`fs.existsSync()` 在 Windows 上瞒过了我

README 一直写着「图片引用缺失 2 处」，我也一直用 `tools/scratch/img-refs.mjs` 验证它。这一轮我把 `data/images-missing.json`（60 条）与实际站点对账，结果**两个数字都对不上**（一个说 2、一个说 23）。

追下去发现根因：**`img-refs.mjs` 用 `fs.existsSync()` 判断图片是否存在，而 Windows 文件系统大小写不敏感**。HTML 里写 `images/Nuclear_Reactor.png`，磁盘上实际是 `images/Nuclear_reactor.png`——`existsSync` 返回 `true`，检查器就放行了。但在 Linux（GitHub Pages、绝大多数静态服务器）上**这就是裂图**。

真实的图片文件是**平铺**的（`site/images` 下 9,326 个文件，无子目录），所以只能逐个精确比对文件名。新增权威检查器 `tools/99f-image-audit.mjs`，用目录真实列举结果做**大小写敏感**比对：

| 类别 | 修复前 | 修复后 |
| --- | --- | --- |
| 名称精确匹配 | 8,430 | **8,445** |
| **仅大小写不同（Linux 上裂图）** | **21 处（涉及 67 个 `<img>`）** | **0** |
| 磁盘上确实不存在 | 2 | **0** |

21 处大小写不匹配的典型例子：`Nuclear_Reactor.png` → 实际 `Nuclear_reactor.png`（3 处引用）、`Super_Heavy_Tank.png` → `Super_heavy_tank.png`（11 处）、`MAS.png` → `Mas.png`（7 处）、`SOMUA.png` → `Somua.png`（7 处）、`Modern_Tank.png` → `Modern_tank.png`（7 处）、`Rocket_engines.png` → `Rocket_Engines.png`（4 处）。

**修复**：不再靠运行环境兜底，而是在构建时把每处引用钉死到磁盘真实文件名。在 `sanitize.mjs` 新增 `setImageCaseMap()` / `resolveImageName()`，`07-build.mjs` 启动时读一次 `site/images` 目录建立小写→真实名的映射：

```js
img.attrs = { src: localImagePath(resolveImageName(nm)), alt: '' };
```

这样生成的 HTML 在**任何**平台上都正确，而不是"在我机器上没事"。

**另外 2 处"确实不存在"也修掉了**：`States_map_nogui.png`、`Diplomacy_map_nogui.png`。这两个用的是 `/thumb.php?f=...&width=300` 动态缩略图形式，直接走 `/images/4/4c/...` 路径是 404（我实测确认），当初因此漏下载。改用 `thumb.php` 形式重取**成功**（95,190 与 91,371 字节，PNG 魔数校验通过），已写入 `site/images/`。

**结果：146,987 处图片引用全部可解析，0 缺失、0 大小写不匹配。** 同时把 `img-refs.mjs` 改成转发到新检查器的提示脚本，避免以后又有人信它。

### 结论（直述，不修饰）

**交付物的「形」已完整达成**：这是一个真正可离线打开、图片全本地、中文可全文搜索、零死链、零外部依赖、已剔除跑题入口的静态网站——这一部分不是「基本完成」，而是**逐项通过机器审计**。

**唯一未达成的条目是「完整翻译」本身**：实测 33.7%，剩余 552 万字符。以本项目实测约 1–2 万字符/轮的速度，补齐剩余部分需要约 **300–500 个额外轮次**，而非本目标的 60 轮。这是**资源上限**导致的未达成，不是难度或方向问题。

**翻译质量分布**是高度不均的，这一点必须明说：
* **已译部分**是逐条经 token 序强制校验、统一术语表约束的，可信度高；但受「占位符必须与英文同序」的硬约束，部分句子中文语序生硬（如「……的第 2 个，用于钢铁雄心 IV」）——这是该技术路线的固有代价。
* **未译部分**在页面上**保留英文原文**，并由页首横幅明确标注进度：`本页中文翻译进度 N%，未译部分暂保留英文原文。` 不存在「假装是中文」的情况。

**本目标继续标记为 active**，未标记完成，也未标记 blocked——因为剩余工作是可行的（只是需要远超 60 轮的迭代），且未遇到任何持续性的外部阻塞条件。若后续追加轮次，可继续按每轮 3–5 个页面推进。

### 60 轮累计方法论沉淀（可复用的部分）

1. **永远不要相信工具的输出，要相信对数据本身的独立检查。** 本项目三次重大误报全部属于此类：`fs.existsSync` 在大小写不敏感文件系统上产生假「缺失」；关键词扫描产生 142 条假「违规」；PowerShell 控制台编码产生假「全站乱码」。三次都是靠针对数据的独立检查（真实目录列举 / 真实链接目标 / Node 码点检查）推翻的。
2. **`token 检查通过 ≠ 已入库`。** 必须直接查翻译记忆库键，或在 rendered HTML 中检索中文串，才能证明翻译真的进入了成品。
3. **用分页命令读取条目列表会静默丢条**（`Select-Object -Skip/-First`），必须核对 `missing=0` 这一硬指标。
4. **连续编辑同一处长文本前，先用 `grep` 确认当前实际内容**，不要假设上一次编辑已生效。
5. **中文语序与占位符顺序冲突时，选择占位符顺序**，把语序调整放进占位符之后的文字里。这个句式（`当/在/如果 X …` 状语前置）在 60 轮中踩中 **16 次**。

## 四、翻译机制说明

* **术语统一**：全站遵循统一术语表（政治点数、国家焦点、国策树、师、支援连、组织度、制空权、顺从度、抵抗度……）。`glossary.html` 是对照表；`tools\glossary-extra.mjs` 与 `tools\short-translate.mjs` 存放跨页面高频词条与短标签的对照规则。
* **结构化翻译**：翻译单元以"段落/表格单元 + 内联占位符 ⟦0⟧"为单位，因此译文里**链接、图标、加粗、表格结构原样保留**，不会出现 HTML 被译坏的情况。
* **增量可续**：翻译记忆库为单文件 `data\tm.json`，同一个英文串全站只译一次；重复构建不会重复翻译。批次文件 `data\batches\batch-NNN.zh.json` 是译文的权威来源，记忆库可随时用 `06c-rebuild-tm.mjs` 重建。
* **未译部分**：若某页仍有未译内容，页面顶部会出现橙色进度条，未译文本保留英文原文——不会出现空白或乱码。
